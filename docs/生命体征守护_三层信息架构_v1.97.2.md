## 一、为什么不做「Apple Watch 健康镜像面板」

最初的方案是把 Apple Watch 能读到的健康指标**全部铺进 App**，做成一个镜像面板，
让用户「不用再回系统健康 App 看」。这个方向被否掉了，原因：

**它丢失了产品的底层逻辑。**

「在呢+」的核心命题是一句话：**让在乎的人知道你很好。**

不是「让你知道自己健康」——那是 Apple 健康 App 的活。人家做了十年、有原生权限、
有专业团队。我们复制过去只有两个结果：**做得更差 + 用户觉得多余**。

所以健康数据在本 App 中的**唯一价值**是回答一个问题：

> 「这个独居的人，可能出事了吗？」

这就是筛选器。一个指标能不能上首屏，不看它多高级，只看**它异常的时候，
守护圈需不需要被惊动**。

| 指标 | 异常时守护圈需要知道吗 | 归属 |
|---|---|---|
| VO2Max 掉 3 个点 | 不需要 | L3 深链 |
| 连续 11 小时零活动 | **必须知道** | L1 首屏头牌 |

## 二、三层结构

### L1 守护级（5 项，首屏常驻）

入选标准只有一条：**异常时守护圈需要被惊动**。

| # | 指标 | 数据 key | 入选理由 |
|---|---|---|---|
| 1 | **今日活动** ★头牌 | `steps` / `exercise_minutes` / `ring_stand_hours` | 独居风险最强信号 |
| 2 | 心率 | `heart_rate` / `heart_rate_min` / `heart_rate_max` | 过高过低均为急症信号 |
| 3 | 血氧 | `blood_oxygen` | <90% 属明确异常 |
| 4 | 步行稳定性 | `walking_steadiness_pct` | Apple 官方跌倒风险指标 |
| 5 | 血压 | `bp_systolic` / `bp_diastolic` | 用户明确要求保留，不置灰 |

**关于头牌「今日活动」**：
独居风险最强的信号从来不是 VO2Max，而是**「这个人今天一动没动」**。
手表在腕上、步数为 0、无运动、无站立 —— 这几个信号叠加，比任何单项生理指标都准。
而 Apple 健康 App **永远不会做这个判定**，因为它不是安全产品。
**这就是我们与它的分水岭。**

**关于步行稳定性**：
Apple 的 Walking Steadiness 本就是为跌倒风险设计的，对独居长者场景高度对口，
是我们最该抓住却一直没用上的一项。

### L2 参考级（6 项，折叠，默认收起）

不触发守护判定，但能为「今日状态」结论提供依据。点一下展开，不占首屏心智。

静息心率 · HRV · 呼吸频率 · 手腕温度 · 行走距离 · 活跃能量

### L3 深链级（不做卡片，一行入口）

| 数据 | 为什么不做卡片 |
|---|---|
| 心电图 ECG | Apple **禁止**第三方读取，硬做只能是假数据 |
| 房颤病史 / 不规则心律 | 同上，永久封闭 |
| 听力暴露 | 对「安全」判定零贡献 |
| 体能 VO2Max | 同上 |

处理方式：一行文字入口「心电图 · 听力 · 体能等完整数据 ›」跳系统健康 App。
**一行，不是十张卡。**

## 三、真正的差异化：不是指标多，是「翻译」

```
Apple 健康说：  静息心率 62 bpm
在呢+ 说：      今天状态平稳，已可向守护圈报平安 ❤️
```

页面顶部新增 **今日状态卡**，由 `SafetySignalEngine` 把 ~70 项原始指标
聚合成**一句人话结论 + 一个可执行动作**。

| | Apple 健康 App | 在呢+ 生命体征守护 |
|---|---|---|
| 目标用户 | 自己看 | **在乎你的人看** |
| 呈现方式 | 数字 + 曲线 | **一句结论 + 一个动作** |
| 指标数量 | 越多越好 | **越少越准越好** |
| 异常时 | 顶多推个通知给你 | **通知守护圈，可一键求助** |

**指标是原料，结论和通知才是产品。**

## 四、「全读 ≠ 全展示」——原生桥为什么保留

`AppDelegate.swift` 的 `getFullHealthSummary` 一次性读取 **~70 项** HealthKit 指标，
虽然 UI 只展示其中十几项，但**必须全读**，理由：

> 判断「长时间无活动」需要同时看步数、运动时长、站立小时、活跃能量、心率波动 ——
> **这些数据必须全读，但一个卡片都不用出。**

多读的数据不上 UI，而是喂给 `SafetySignalEngine` 做异常判定。

**底层能力全开，UI 保持克制。这是最优解，不是二选一。**

## 五、中国合规版红线（必读）

`SafetySignalEngine` **只做本机判定与展示，不含任何自动外发**。

若后续要接「异常 → 自动通知守护圈」，**必须**包 `!AppConfig.isChinaRegion` 闸门：
- 海外版：可自动外发
- CN 版：仅本机提醒 + 用户手动确认后外发

这正是当初中国区被判定 "dead-man switch" 下架的那根红线，**不能再踩**。

## 七、异常自动外发（海外版专属能力）

### 为什么这才是闭环

前面把 70 项指标翻译成一句结论，只完成了一半。**结论如果只有本人看得到，就还是一个健康 App。**
真正的差异化在最后这一步：**检测到异常时，替用户主动通知家人。**

| | Apple 健康 App | 在呢+ |
|---|---|---|
| 检测到异常 | 顶多推个通知给**你自己** | **自动通知守护圈** |

### 实现

`HealthService._evaluateSafetySignal(summary)`，挂在 `syncHealthData()` 尾部，
每次健康同步（App 启动 / 前后台切换）自动执行。

- **触发条件**：`SafetySignalEngine` 判定为 `SafetyLevel.alert`（如 18 点后 <60 步且无运动无站立）
- **冷静期**：6 小时，同一异常不重复打扰守护圈
- **与 `checkAnomalies` 分工**：后者管单项生理指标越界（心率/血氧），本方法管**安全维度**（长时间无活动），二者独立冷静期、互不覆盖
- **容错**：判定失败只打日志，绝不影响主同步流程

### 双重闸门

```
① 区域合规闸门  AppConfig.isChinaRegion  → CN 恒关，用户不可开
② 用户自主开关  safety_auto_alert_enabled → 海外版默认开，可自行关闭
```

`HealthService.isSafetyAutoAlertEnabled()` 在 CN 版直接 `return false`，
UI 开关也整个不渲染（`if (!AppConfig.isChinaRegion)`），**双保险**。

关闭时（无论哪种原因）异常只写入本地 `pending_safety_alerts`，不外发。

### 🔴 顺带修掉一个既有合规隐患

审计时发现 `health_service.dart:612`（原行号）的 `sendHealthAlert(alerts)` —— 也就是
**既有的健康异常自动报警 —— 此前完全没有区域闸门**。它由首页启动时的
`_syncHealthData()` 自动触发，意味着 **CN 版一直存在自动向守护圈外发的路径**，
正是 Apple 判定 dead-man switch 的行为。本次已补上闸门。

**全项目自动外发调用点闸门审计结果（7/7 全部受控）：**

| `health_service.dart:709` | 安全信号报警 | ✅ 双重闸门 |
